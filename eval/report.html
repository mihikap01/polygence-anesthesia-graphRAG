GraphRAG eval · 4 arms × 187 held-out PharmGKB questions

Does graph structure actually help an LLM answer pharmacogenomics questions?

A blinded, falsifiable, four-arm evaluation of the Polygence GraphRAG demo, with cross-checks designed to reveal what LLM-as-judge can and cannot detect.

TL;DR

We tested whether a knowledge-graph layer (GraphRAG) over PharmGKB pharmacogenomic data produces better answers than a frontier LLM alone, or than the same LLM with strong plain-text retrieval. Across 187 held-out questions, GraphRAG (A3) tied strong hybrid retrieval (A1) on blinded pairwise preference (48.9%, p=0.83) — H1 was not supported.

The deeper finding: across four independent metric families (preference, rule-based, rubric ratings, merged-claim hallucination), the LLM judge consistently preferred the model's own no-context answers — even though those answers fabricated specific PMIDs 68.3% of the time (vs. 33.3% for GraphRAG). GraphRAG is more grounded; the judges can't tell.

The one place GraphRAG did win cleanly was out-of-distribution refusal — knowing what the graph does not contain. The structural value of the graph in this domain is "knowing the boundaries," not "multi-hop reasoning."

1 · the setup

What we built and what we're testing

The project under test is a pharmacogenomic GraphRAG demo: a knowledge graph built from PharmGKB clinical-variant data, paired with a retrieval pipeline that extracts the relevant subgraph for a question and feeds it to an LLM. The system claims that structuring the data as a graph — and retrieving via graph traversal — produces more grounded, more specific, less hallucinated answers than a frontier LLM produces on its own.

This evaluation tries to measure whether that claim holds, and crucially whether the benefit comes from the graph structure itself or just from "having any retrieved context at all" (which a much simpler text-similarity retriever would also provide).

2 · the data

PharmGKB — what's in the dataset

PharmGKB is the open clinical pharmacogenomics database. The backbone we use is clinicalVariants.tsv — about 5,200 curated rows, each linking a genetic variant to a drug (and often a disease phenotype), with a peer-reviewed evidence level (1A = strongest, 4 = weakest).

3 · how we made it a fair test

The held-out split

The core challenge for any eval against a system built on PharmGKB is contamination — both the system and any sensible test question source come from PharmGKB. If we just asked questions sourced from rows the graph already contains, GraphRAG would always "win" by lookup, not by reasoning.

1
Start with the 400 high-evidence rows. These are the clinically meaningful 1A/1B/2A/2B associations in PharmGKB.
↓
2
Randomly hold out 30% (120 rows). Deterministic seed (42) so the split is reproducible.
↓
3
Rebuild the graph WITHOUT those rows — the same flag also strips them from A1's text-retrieval index. Neither GraphRAG nor naïve RAG can "lookup" the answers from the exact held-out rows.
↓
4
Generate 187 questions from those held-out rows, using templates per question-type (see §6). The facts are real PharmGKB knowledge but the exact rows are unseen by every arm.

Reduced graph: 3,203 nodes / 7,972 edges (vs the full 3,213 / 8,024 — small reduction because most graph edges have multiple supporting rows).

The 4 arms — same model, only the context differs

All four arms use the same generator model (Claude Sonnet 4) with the same system prompt (see §5). The only variable is what context the model receives alongside the question. This is what isolates "what graph structure adds" from "what retrieval adds" from "what the model already knows."

8 · how we measured

Four independent metric families

The eval intentionally uses multiple independent measurement approaches, because each one has different failure modes. Convergent results across all four = real signal.

1
Rule-based metrics (deterministic Python). PMID exists in our corpus, entity precision/recall vs gold, evidence-level exact-match, refusal correctness. Same definition across all arms — no arm is structurally penalised.
2
Pairwise preference (the H1 headline). For each question, Claude Haiku 4.5 sees both answers blinded, randomised order, picks the better one. n=374 comparisons (A3 vs A1 + A3 vs A0). Sign-test p value.
3
Rubric ratings (Faithfulness / Completeness / Clinical-soundness 1–5). Haiku rates each answer against ground truth (not arm-specific context — that asymmetry was a v1 bug we fixed). Targets coverage 748; achieved 445 before CLI hangs.
4
Merged-claim hallucination. Per question, judge extracts the union of atomic factual claims across all 4 answers, then marks each as supported / unsupported / unverifiable vs ground truth. Same denominator across arms.
The judge — Claude Haiku 4.5, cross-size within Claude Generator was Claude Sonnet 4 (frontier); judge was Claude Haiku 4.5. Within-family judging is a known weaker mitigation than cross-family (Gemini judging Claude) — declared as a threat. We compensate by leaning on the deterministic rule-based metrics (judge-independent) and on convergence across the four metric families.

11 · why this happened

The deeper finding — preference ≠ correctness

Key findings

H1 (primary): NOT SUPPORTED GraphRAG (A3) vs. strong naïve RAG (A1): 48.9% A3-preferred (91–95, sign-test p=0.826). This is a statistical tie — the graph layer did not beat strong hybrid retrieval on this question set. The pre-registered bar was >55% with p<0.05.
  • H2 (multi-hop): not supported. On S3 (multi-hop), A3 was preferred only 42.5% of the time — it lost to A1. This matches the hostile reviewer's prior: PharmGKB rows are already denormalised, so a strong retriever recovers multi-hop facts without needing graph traversal.
  • H3 (no regression): mild regression. On S1 (well-known facts) A3 was preferred only 35.0% vs A1 — the extra graph context reads as noise on trivially-known questions.
  • A3's one genuine win: out-of-distribution refusal (S7, 60.0%). When a drug isn't in the graph, A3 cleanly refuses; A1's retrieval always returns something, tempting it to answer. This is the clearest evidence that graph structure helps — knowing what's absent.
  • A3's apparent S4 win (96.0%) is a confound, not a win. The held-out split removed clinicalVariants rows but not relationships.tsv rows, so A1 could still retrieve the (correct) PMIDs while A3's graph genuinely lost them. The judge then preferred A3's refusal over A1's correct citation — rewarding caution over verifiable grounding.
  • The meta-finding — preference ≠ correctness. A0 (no context) "won" the preference test (27.8% A3-preferred, p=0.0000 — i.e. A0 strongly favoured), yet A0's cited PMIDs were real only 31.7% of the time vs. 66.7% for A3. The LLM judge is fooled by fluent, confident prose and cannot detect fabricated citations. This is precisely why the design pairs subjective preference with deterministic rule-based metrics.
Bottom line On this PharmGKB-derived benchmark, with Claude Sonnet as the generator, the GraphRAG layer did not demonstrate an advantage over strong hybrid retrieval, and both retrieval arms were dispreferred by the LLM judge relative to the model's own parametric answers — which are themselves unreliable (high PMID fabrication). The honest conclusion: for this domain and model, the value of the graph is concentrated in knowing what it does NOT contain (refusal), not in multi-hop reasoning. See the threats/deviations section for why these numbers should be read with caution.
All four metric families say the same thing
  • Pairwise preference: A0 preferred over A3 in 72% of comparisons.
  • Rubric Faithfulness (1–5): A0 3.49, A1 3.43, A3 3.07. Judge rates A0 highest.
  • Merged-claim support rate: A0 74.1%, A1 69.1%, A3 66.6%, A2 55.1%.
  • Rule-based PMID-exists: A0 31.7% (i.e. fabricates 68.3%), A3 66.7%.
A0 has strong parametric pharmacogenomic knowledge — its substantive claims are largely correct. But it fabricates specific PMIDs at a high rate that the LLM judge cannot detect. The judge rewards fluent confidence; the rule-based metrics see the lies.

  • Single model, single judge, n≈25–40 per stratum. Per-stratum numbers are descriptive, not inferential. Only the n=187 pairwise test is adequately powered.
14 · what this means + what's next

So what?

This is a mixed-to-negative result, and a more useful one than a clean sweep would be. It shows:

  • For this domain (pharmacogenomics) and this dataset (PharmGKB), graph structure doesn't reliably beat strong hybrid retrieval. The reason is structural: PharmGKB rows are already denormalised — drug, gene, variant, phenotype, and evidence level all appear together in a single row — so a text retriever can reach "multi-hop" facts without actually traversing a graph.
  • The structural value of the graph lives in refusal, not in reasoning. When a drug isn't in the graph, A3 refuses cleanly; A1's retrieval always returns something, tempting hallucination.
  • LLM-as-judge cannot detect fabricated PMIDs. A0 cited fake PMIDs 68% of the time and still won the preference test. Any eval relying solely on preference is measuring fluency, not correctness.

Concrete next steps to make this a stronger eval

  • Also hold out relationships.tsv rows that restate the same facts — removes the leakage that gave A1 the S4 citation advantage.
  • Cross-family judging (Gemini or GPT judging Claude) to remove the within-Claude self-preference bias.
  • Test in a less-denormalised domain. PharmGKB rows do half of GraphRAG's work for free. Drug-interaction networks, gene-pathway graphs, or biomedical literature graphs (where multi-hop ≠ single-row lookup) would be a fairer test of structural value.
  • Inline PMIDs in A3's context. The web app's chat flow doesn't feed PMIDs to the model (they go to the UI as separate chips). That's a real product limitation — A3 cannot do citation grounding even though the graph has the PMIDs.
  • Hand-rate 20 answers to calibrate Haiku's preferences vs human (preregistration §8.4, still not done).
