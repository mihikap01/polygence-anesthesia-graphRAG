Polygence research report · pharmacogenomic knowledge-graph RAG

Does subgraph retrieval over a knowledge graph outperform plain-text retrieval for pharmacogenomic question answering?

Mihika Pall · Polygence (2026). An evaluation of three RAG architectures on 187 held-out PharmGKB questions, with rule-based and LLM-judge scoring.

Abstract

We evaluate whether subgraph-RAG over a curated pharmacogenomic knowledge graph (PharmGKB) produces better question-answering than (i) a frontier LLM with no retrieved context, or (ii) the same LLM with a strong hybrid plain-text retriever (BM25 + dense embeddings, RRF, top-K). We compare these three retrieval conditions on 187 questions derived from a 30% held-out partition of PharmGKB's high-evidence clinical-variant rows, across eight question strata. The primary outcome is blinded pairwise preference judged by Claude Haiku 4.5; secondary outcomes include deterministic rule-based metrics, anchored 1–5 rubric ratings, and merged-claim hallucination rate.

Subgraph RAG did not outperform plain-text RAG on the primary preference test (48.9% A3 wins, sign-test p=0.83). The no-context model was preferred most often by the judge despite fabricating cited paper identifiers (PMIDs) at a rate of 68.3%, versus 33.3% for subgraph RAG — evidencing that LLM-as-judge rewards fluent confidence over factual grounding. The graph layer's only consistent advantage was appropriate refusal on out-of-distribution queries. We attribute the null primary result to PharmGKB's row-level denormalisation, which packs multi-hop facts into single text chunks and thereby allows strong text retrieval to recover them without graph traversal. We discuss confounds (notably partial held-out leakage via relationships.tsv) and propose targeted follow-up experiments.

1 · introduction

1. Introduction

Retrieval-augmented generation (RAG) systems are increasingly proposed for biomedical question answering, where the cost of fabricated facts is high. A growing literature argues that knowledge-graph-based RAG — retrieving a relevant subgraph instead of text chunks — should outperform plain-text RAG by preserving entity relationships, evidence provenance, and multi-hop reasoning paths.

This report tests that claim concretely. We evaluate a subgraph-RAG implementation built over PharmGKB, the curated pharmacogenomic knowledge base, focused on anesthesia and pharmacogenomic-risk reasoning. We compare it against (a) the same frontier LLM with no retrieved context (a parametric-knowledge baseline) and (b) the same LLM with a strong hybrid text retriever over the same data. The primary test is blinded pairwise preference; secondary tests are rule-based grounding metrics, anchored rubric ratings, and a per-claim hallucination metric using merged-claim segmentation.

2 · background

2. Background

RAG architectures. The classical RAG pipeline chunks text, indexes chunks via similarity search, and concatenates the top-K matches into the LLM's prompt. Subgraph RAG instead indexes the source data as a knowledge graph: at query time the question is entity-linked to graph nodes, the system extracts a relevant subgraph (neighborhoods of linked entities and/or shortest paths between them), and renders that subgraph as text for the LLM. We refer to the system under test as "subgraph RAG" following common usage. Note that this is distinct from Microsoft GraphRAG (Edge et al., 2024), which additionally pre-computes LLM-generated summaries of automatically-detected graph communities and retrieves over those summaries — a step we did not implement.

The claim under test. Subgraph RAG should improve over text RAG when (i) the graph captures relationships that are not co-located in single source documents, (ii) the question requires reasoning across multiple such relationships, and (iii) the generator benefits from explicit relationship structure in its prompt. The PharmGKB demo makes these claims for pharmacogenomic question answering. We test whether they hold under a blinded, held-out evaluation.

3.2 Held-out split

A core methodological challenge: both the system under test and any in-distribution question source come from PharmGKB. Naive question generation would let subgraph RAG "win" by lookup rather than reasoning. We address this with a deterministic train/test split:

  1. Restrict to the 400 high-evidence clinical-variant rows (levels 1A/1B/2A/2B).
  2. Randomly select 30% (120 rows) as held-out. Seed fixed at 42 for reproducibility.
  3. Rebuild the graph without these rows. The same flag also strips them from the plain-text retriever's index, so neither A1 nor A3 can recover them by direct lookup.
  4. Generate 187 questions from those held-out rows using stratum-specific templates (§3.5).

The reduced graph contains 3,203 nodes and 7,972 edges (reduction is small because most graph edges have multiple supporting source rows). The 120 held-out rows yield 187 test questions across 8 question types.

3.3 The three retrieval conditions (arms)

The three arms use the same generator (Claude Sonnet 4) with the same system prompt (§3.4). The only variable across arms is the context provided alongside the question, allowing us to isolate the effect of retrieval (A0 vs. A1/A3) and the effect of graph-native vs. text-similarity retrieval (A1 vs. A3).

A3 · subgraph RAG (system under test)

Entity-linking → 1-hop neighborhood → shortest-path expansion

For each question: (1) fuzzy-match question tokens against the graph's 3,203 nodes via the search index to identify mentioned entities (up to 6, by score); (2) extract each linked entity's 1-hop neighborhood of edges; (3) compute BFS shortest paths between every pair of linked entities, up to 4 hops, preferring edges flagged CRITICAL or evidence-level 1A/1B; (4) render the result as a structured text block with explicit sections for entities, neighborhoods, and paths. A purely text-similarity system cannot perform steps 1, 2, or 3.

On terminology. A3 is what the literature usually calls "subgraph RAG" — query-conditional retrieval of a relevant subgraph, rendered for the LLM. We do not implement Microsoft GraphRAG (Edge et al., 2024), which adds an offline community-detection and LLM-summarisation step. Our test concerns the subgraph-RAG variant because that is the architecture the demo ships.

Why three arms, not four. A fourth condition (A2 — a static dump of a hand-curated 36-node anesthesia subgraph) was generated and retained in the raw data (eval/answers.jsonl). On reflection, A2 conflated "graph context absent" with "graph context off-topic" — its context was the same fixed subgraph for every question regardless of relevance. We omit it from analysis to keep the comparison between three architecturally distinct conditions: no retrieval, text retrieval, graph retrieval.

3.7 Evaluation protocol

Four independent measurement approaches are used; their disagreement modes are complementary, so convergence across all four is treated as the strongest signal.

  1. Rule-based metrics (deterministic Python). PMID existence in our corpus, entity precision and recall against the gold entity set, evidence-level exact-match (for the relevant stratum), and refusal correctness (for negative-control and out-of-distribution strata). Same definition across arms.
  2. Blinded pairwise preference (Claude Haiku 4.5 as judge). For each question, the judge sees two answers with arm labels stripped and order randomised, then picks the preferred answer or "tie." A3 vs. A1 is the primary headline; A3 vs. A0 is secondary. We report sign-test p-values and Wilson-score 95% confidence intervals.
  3. Anchored rubric ratings (1–5). Same judge rates each answer independently on Faithfulness, Completeness, and Clinical soundness against ground truth (not against arm-specific retrieved context, which would penalise A0 by construction).
  4. Merged-claim hallucination rate. Per question, the judge extracts the union of atomic factual claims across all four arms' answers, then marks each as supported / unsupported / unverifiable against ground truth. Same merged claim list yields the same denominator across arms, making the comparison fair.

Generator / judge configuration. Generator: Claude Sonnet 4 via the Claude Code CLI. Judge: Claude Haiku 4.5 via a separate CLI session. This within-family size split partially mitigates self-preference bias (a known weakness of LLM-as-judge when generator and judge share parameters); a cross-family judge (e.g. Gemini judging Claude) would be stronger and is listed as a methodological improvement in §7.

5 · discussion

5. Discussion

5.1 Why subgraph RAG did not beat plain-text RAG

Primary verdict: H1 NOT SUPPORTED When the blinded judge compared GraphRAG's answer to plain-text RAG's answer on the same question, GraphRAG was picked 48.9% of the time (91 wins out of 186 decisive comparisons). The pre-declared "win" threshold was >55% with p<0.05. We got p=0.83 — meaning the difference is indistinguishable from pure chance. GraphRAG did not earn its complexity on this benchmark.
  • The multi-hop test (H2): also lost. Questions specifically designed to require reasoning across multiple graph edges — exactly where the structure should shine — had GraphRAG winning only 42.5% of the time vs plain-text RAG. The reason: PharmGKB rows already pack drug + gene + variant + phenotype + evidence level into a single row, so a good text retriever recovers "multi-hop" facts in a single chunk without needing graph traversal.
  • On easy questions (H3): mild regression. Even on well-known facts where adding context shouldn't matter, GraphRAG was picked only 35.0% of the time — the extra graph context reads as noise when the answer is trivially known.
  • The one genuine win: knowing what the graph doesn't contain. On questions about drugs the graph genuinely lacks (out-of-distribution test), GraphRAG was preferred 60.0% of the time. It says "I don't have that"; plain-text retrieval returns vaguely-related junk and the model answers confidently. Knowing the boundaries of the data is the graph's structural value, not multi-hop reasoning.
  • The apparent citation win is a confound, not a real win. On citation-grounding questions GraphRAG was picked 96.0% of the time — but the reason isn't grounding. The held-out test set removed one PharmGKB file but not another that restates many of the same facts. Plain-text RAG could still retrieve correct PMIDs from the un-held-out file; GraphRAG's graph genuinely lost them and refused to cite. The judge rewarded refusal over correct citation. The metric is measuring caution, not truth.
  • The meta-finding: preference ≠ correctness. The no-context model (just the LLM, no retrieved data at all) was picked 72.2% of the time over GraphRAG — a strong win. But when we checked whether its cited paper IDs (PMIDs) were real, only 31.7% actually existed. GraphRAG's cited PMIDs were real 66.7% of the time. The LLM judge was fooled by fluent confidence and couldn't detect fabricated citations. This is the entire reason the design uses both subjective preference and deterministic ground-truth checks.
Bottom line On this PharmGKB-derived benchmark, with Claude Sonnet as the generator, the GraphRAG layer did not demonstrate an advantage over strong hybrid retrieval, and both retrieval arms were dispreferred by the LLM judge relative to the model's own parametric answers — which are themselves unreliable (high PMID fabrication). The honest conclusion: for this domain and model, the value of the graph is concentrated in knowing what it does NOT contain (refusal), not in multi-hop reasoning. See the threats/deviations section for why these numbers should be read with caution.

5.2 Convergence across metric families

Four independent measurement approaches were used. They agree:

  • Pairwise preference: A0 preferred over A3 in 72% of comparisons.
  • Rubric Faithfulness (1–5): A0 = 3.49, A1 = 3.43, A3 = 3.07. The judge rates A0 highest.
  • Merged-claim support rate: A0 = 74.1%, A1 = 69.1%, A3 = 66.6%.
  • Rule-based PMID-exists: A0 = 31.7% (i.e. fabricates 68.3%), A3 = 66.7%.

A0 has strong parametric pharmacogenomic knowledge — its substantive claims are largely correct (74% support rate). But it fabricates specific paper identifiers (PMIDs) at a high rate the LLM judge does not detect. The judge rewards fluent confidence; only the deterministic rule-based metrics catch the fabrication. This is the principled reason for not relying on LLM-judge preference alone in high-stakes evaluations of retrieval systems.

5.3 Where subgraph RAG did help: out-of-distribution refusal

The one stratum where A3 outperformed A1 was S7 (out-of-distribution drugs not in the graph). When a query referenced an entity the graph genuinely lacks, A3 returned an empty subgraph and appropriately refused; A1's text retriever always returns something — semantically related noise — which the model interpreted as license to answer. This is consistent with the view that the structural value of a knowledge graph in this domain is boundary knowledge (what is present vs. absent) rather than multi-hop reasoning.

5.4 Why this domain is harder than expected for graph RAG

PharmGKB's clinicalVariants.tsv is heavily denormalised: a single row routinely contains variant + gene + evidence level + drugs + phenotypes. "Multi-hop" facts that would require graph traversal in a normalised schema are recoverable in a single text chunk by any sensible text retriever. We conjecture that the absence of a measured benefit for the graph layer in this evaluation reflects this denormalisation, not a deficiency in subgraph RAG as an approach. Domains whose data is genuinely fragmented across documents (e.g. drug-drug interaction networks, citation graphs, multi-source knowledge bases) would be expected to differentiate the approaches more sharply.

6 · limitations

6. Limitations and threats to validity

The following limitations and protocol deviations should be borne in mind when reading the headline result.

6.1 Generator and judge configuration

The pre-registration named Claude Opus as the generator; we used Claude Sonnet 4 for cost and throughput (~10× cheaper, ~3× faster per call). A stronger generator might raise A0's parametric-knowledge quality further, which would strengthen the pattern reported here (A0 fluent and confident, retrieval arms struggling to improve on it) rather than weaken it. The judge was Claude Haiku 4.5 — a smaller model in the same family — which partially but not fully mitigates self-preference bias. A cross-family judge (Gemini or GPT) would be a methodological improvement.

6.2 Partial held-out leakage via relationships.tsv

The held-out split removes rows from clinicalVariants.tsv but not from relationships.tsv, which redundantly restates many of the same drug-gene associations along with PMIDs. The plain-text retriever (A1) indexes both files and could therefore still retrieve correct PMIDs for associations whose clinicalVariants row had been held out. The subgraph-RAG arm (A3) genuinely lost those edges from its graph. The S4 (citation) result is the most affected — the judge in some cases preferred A3's refusal to cite over A1's correct-but-unverifiable citation, which conflates "refusal" with "grounding." A cleaner v2 should hold out the corresponding relationships.tsv rows in parallel.

6.3 The plain-text RAG baseline (A1) is strong but not maximal

The A1 spec uses BM25 + sentence-transformers/MiniLM dense embeddings fused via reciprocal-rank fusion, with the top-8 chunks in the prompt. The pre-registration originally included a BGE cross-encoder reranker, which was dropped to keep the local install lightweight. Adding the reranker would be expected to further strengthen A1 — which would, if anything, make the conclusion stronger (graph structure adds even less over a maximally-tuned text retriever) rather than weaker.

6.4 Production subgraph-RAG does not surface PMIDs to the model

The web app's chat endpoint extracts PMIDs into a separate UI-side citations list but does not include them in the LLM's prompt. We faithfully ported this behaviour into A3 for the evaluation. As a result, A3 cannot ground PMIDs in the way A1 can, even when the graph has them. This is a real product limitation, not an evaluation artefact; fixing it (inlining PMIDs into the rendered subgraph) is a top-of-list improvement (§7).

6.5 Sample size and inferential scope

The primary n=187 pairwise test is adequately powered (sign-test, >0.95 power to detect a 55% preference rate at α=0.05). Per-stratum sample sizes (n=12–40) are not adequately powered after multiple-comparison correction; per-stratum results are reported as descriptive context rather than as inferential claims. Coverage of the rubric and segmentation passes was reduced (60% and 31% respectively) by intermittent Claude CLI hangs, which disproportionately affected the late strata (S7, S8).

7 · conclusions

7. Conclusions and future work

On a held-out PharmGKB benchmark, with Claude Sonnet as the generator and Claude Haiku as the judge, the subgraph-RAG system we evaluated did not outperform a strong plain-text RAG baseline on blinded pairwise preference (49% A3-preferred, p=0.83). Across four independent metric families — preference, deterministic rule-based, anchored rubric ratings, and merged-claim hallucination — the no-context model received the highest judge ratings despite fabricating cited PMIDs at roughly twice the rate of subgraph RAG. The graph layer's one consistent advantage was appropriate refusal on out-of-distribution queries.

The most parsimonious explanation for the null primary result is that PharmGKB's row-level denormalisation packs ostensibly multi-hop facts into single text chunks, allowing strong text similarity to recover them. The result therefore says something specific about this domain (and arguably about any heavily denormalised knowledge graph) rather than something general about subgraph RAG.

7.1 Targeted follow-up experiments

The following experiments would each test a specific hypothesis raised by these results and are listed in increasing implementation cost:

  1. Remove the relationships.tsv leakage. Hold out the corresponding rows in relationships.tsv in parallel with clinicalVariants.tsv; re-run. Cleanest test of whether the leakage is what kept A1 competitive on citation-grounding.
  2. Inline PMIDs into A3's context. A ~10-line change in eval/retrieve_py.py to surface edge-level PMIDs in the structured prompt. Re-run the citation stratum only. Likely converts A3's confounded refusal-win on S4 into a real grounding win.
  3. Cross-family judge. Re-run the pairwise and rubric passes with Gemini 2.5 as judge. Removes within-Claude self-preference; tests whether the "A0 preferred" result is family-specific.
  4. Hybrid arm (A4 = A3 + A1). A natural product question: does concatenating A3's structured subgraph and A1's top-3 text chunks produce a system that strictly dominates either alone?
  5. Architectural variants. Implement a Microsoft-style GraphRAG arm (Leiden communities + LLM-generated community summaries + hierarchical retrieval) to test whether community-level summarisation succeeds where edge-level retrieval did not.
  6. Cross-domain replication. Run the same evaluation harness on a less denormalised knowledge graph (drug-drug interaction networks, citation graphs, gene-pathway networks) where multi-hop facts genuinely require traversal. This is the cleanest test of whether the negative result here generalises beyond PharmGKB.

A.3 — Metric family 1: rule-based (deterministic, judge-independent)

What it measures

Hard, verifiable facts about each answer:

  • PMID exists rate — of cited PMIDs, the fraction that actually appear in our corpus (relationships.tsv + PubMed). Detects citation fabrication.
  • Entity precision / recall — of the gold entities (genes, drugs, phenotypes) for the question, how many appear in the answer.
  • Evidence-level exact match — (S2 stratum only) does the claimed evidence level (1A / 1B / 2A / 2B / 3 / 4) match the gold level?

This is the only metric family that is judge-independent. It cannot be biased by which model the judge prefers. If the LLM judge and the deterministic checks disagree, the deterministic check is the ground truth signal.

A.4 — Metric family 2: blinded pairwise preference (the H1 primary test)

What it measures

For each question, Claude Haiku 4.5 sees two answers (e.g. A3 and A1) with arm labels stripped and presentation order randomised, then picks the preferred answer or "tie." We run two pairs per question: A3 vs A1 (primary, 187 comparisons) and A3 vs A0 (secondary, 187 comparisons), for 374 total.

Why we use it

Pairwise comparison is the most defensible form of LLM-as-judge — it requires less anchoring than 1–5 absolute ratings and is robust to scale-use bias. With n=187 the sign-test has >0.95 power to detect a 55% preference rate at α=0.05. This is the only adequately powered hypothesis test in the design.

How H1 is decided

Pre-registered threshold (frozen before any LLM calls): A3 wins H1 if A3 is preferred on >55% of decisive comparisons with sign-test p<0.05.

A.5 — Metric family 3: anchored 1–5 rubric ratings

What it measures

Per answer, Claude Haiku rates three dimensions on a 1–5 scale anchored to verbal descriptions:

  • Faithfulness (1–5) — does every factual claim match ground truth? 5 = all claims supported · 3 = some wrong/unverifiable · 1 = many fabricated
  • Completeness (1–5) — does the answer cover the gold entities and relationships? 5 = covers gold + sensible elaboration · 1 = misses the central fact
  • Clinical soundness (1–5) — would a pharmacist call this misleading or unsafe? 5 = clinically appropriate, well hedged · 1 = misleading / unsafe

Crucially, the judge sees question + gold + answer — not arm-specific retrieved context. This avoids penalising A0 (no context) by construction.

Why we use it

Captures softer qualities (clinical caution, completeness) that the rule-based pass can't. Less powerful than pairwise but gives anchored absolute scores.

A.6 — Metric family 4: merged-claim hallucination rate

What it measures

Per question, Haiku extracts the union of atomic factual claims across all 4 answers (with arm labels stripped), then labels each claim as supported / unsupported / unverifiable against ground truth. For each arm we count: how many of those claims did the arm make, and how many were supported.

Hallucination rate = (unsupported claims the arm made) / (total claims the arm made). Same merged claim list → same denominator across arms, which makes the comparison fair (the previous version used per-arm segmentation, which gave terse arms a structural advantage).

Why we use it

Pairwise preference can't see fabrication; the judge prefers fluent confidence. This metric exposes per-arm fabrication rate with a fair denominator. It is the only cross-arm-comparable hallucination measure.

Appendix B. Which prompts actually let GraphRAG beat the baselines?

The headline (§4.1) says A3 ties A1 on average. But "average" hides structure. This appendix mines the same 374 pairwise judgments + 748 rule-based scores to find which specific prompt patterns let GraphRAG win decisively against both A0 and A1. The goal: an evidence-based answer to "when should I actually use GraphRAG?"

B.1 — Method

We filter to prompts where A3 won pairwise against both A0 and A1 — meaning the Haiku judge preferred A3 over the no-context model AND over plain-text RAG. Then we cross- check against the rule-based metrics (entity recall, PMID exists, refusal correctness) to separate substantive wins (corroborated by ground-truth checks) from style-only wins (judge liked the prose but factual scores neutral).

Out of 187 questions, 35 are A3 double-wins on pairwise; of those, 7 are substantively corroborated by rule-based metrics. The other 28 are judge-style wins we don't lean on.

B.2 — The four prompt patterns where GraphRAG wins

Pattern 1 · "Is this drug in the database?" — out-of-distribution queries

Win rate: 33% of S7 (5/15 OOD questions). GraphRAG's highest-conviction win.

When a user asks about a drug, herbal supplement, or OTC product that is genuinely not in the curated graph, GraphRAG's entity-linker returns an empty match list and the answer can cleanly say "this entity is not in the graph." Plain-text RAG always returns something (semantically related noise), tempting the model to fabricate.

Example prompt (real, from the eval — question S7-006):

"What pharmacogenomic guidelines exist for saw palmetto in PharmGKB?
Cite the specific gene-drug interactions if any."

Why A3 wins:

  • A3's entity-linker finds zero matches in the 3,213-node graph → answer states this directly.
  • A1's BM25 + dense retriever surfaces tangentially-related rows (other herbal supplements, anything mentioning "supplement"), and the answer drifts into uncertain territory.
  • A0 (parametric) sometimes guesses confidently from training data.

Use this pattern when:

  • You're not sure whether a drug is covered by PharmGKB clinical guidelines
  • You're triaging a list of supplements / OTCs / niche compounds for review
  • You need an honest "no, this isn't curated" signal rather than a fluent guess

Why this works — the mechanism:

Graph traversal can prove absence; text similarity cannot.

The retrieval pipelines behave asymmetrically when a query concerns a missing entity:

  • A1 (text search) always returns its top-K nearest chunks by cosine similarity — even the least-similar match still comes back. The LLM sees something in its context and reads that as "yes, there's data here."
  • A3 (graph traversal) begins with entity linking: a discrete lookup against the 3,213-node search index. If no node matches at the required similarity threshold, the result is an empty list — a distinct signal that the entity is not represented, which flows into the prompt verbatim as ENTITY LINKING: no specific graph entities matched.

The empty result is a truth-preserving signal that maps 1:1 onto the correct answer ("no, it isn't in the graph"). A1's non-empty result is a truth-obscuring signal that misleads the LLM into speculating.

Pattern 2 · "Is there a clinical association between X and Y?" — negative-control queries

Win rate: 32% of S6 (8/25 negative-control questions).

When the user asks about a specific drug-gene pair that PharmGKB has explicitly evaluated and judged as not associated, GraphRAG can inspect the linked entity's neighborhood and report the absence of an edge directly. Other arms tend to assert an association from parametric memory or partial retrieved evidence.

Example prompt (real, from the eval — question S6-001):

"According to PharmGKB-curated evidence, is there a clinically
meaningful pharmacogenomic association between
hydrochlorothiazide and FGF5?"

Why A3 wins:

  • A3 entity-links both terms, pulls hydrochlorothiazide's full 1-hop neighborhood (31 gene edges, all efficacy/toxicity for unrelated genes), and confirms FGF5 is absent.
  • A0 sometimes hallucinates a plausible-sounding mechanism.
  • A1 retrieves general hydrochlorothiazide chunks but doesn't necessarily catch the FGF5 absence.

Use this pattern when:

  • Cross-checking a hypothesis ("could X be the gene driving Y's response?")
  • Verifying that a claim from another source is actually supported in PharmGKB
  • You need "no, this association is not curated" with backup evidence

Why this works — the mechanism:

Neighborhood enumeration turns "is there an edge?" into a bounded set-membership test.

The question "is there an association between X and Y?" requires proving a negative — the hardest thing for a language model to do reliably, because absence rarely has direct textual evidence.

  • A3's context for this question includes X's full 1-hop neighborhood: every edge incident to X, each labelled with its type and evidence level. That's a closed set. The LLM can literally scan the set for Y — if Y is present, it's supported; if Y is absent, that too is grounded in the context.
  • A1's context is the top-K text chunks about X — an open set. The LLM cannot conclude that "Y is absent from the top 8 chunks" implies "Y is not associated," because the retriever may have missed the relevant chunk. Uncertainty spirals into hedging.
  • A0 has no closed set at all — it must recall a fact it may never have seen.

The concrete win, from the eval: A3's answer explicitly cited "31 gene edges, none are FGF5" — a claim only makes sense against a closed-set context. A1 could only say "none of the 8 retrieved chunks mention FGF5," which is weaker evidence.

Pattern 3 · "What does PharmGKB say about <niche-drug> and <gene>?" — long-tail entity disambiguation

Win rate: 28% of S5 (7/25 niche-drug questions).

For obscure drug-gene pairs, GraphRAG often catches entity confusions the other arms walk into. The structured entity linker either fails to match (returns empty) or returns the exact entity, which surfaces "did you mean a similarly-named drug?" issues that A0 and A1 paper over.

Example prompt (real, from the eval — question S5-006):

"What pharmacogenomic relationship has PharmGKB documented
between methazolamide and HLA-C? Be specific about the type
(metabolism / efficacy / toxicity)."

Why A3 wins:

  • A3 reports "no methazolamide–HLA-C edge in the supplied context" and explicitly flags a potential entity mismatch (the user may have meant acetazolamide).
  • A1 retrieves something related and confidently asserts a relationship type.
  • A0 invents a plausible mechanism from training data.

Use this pattern when:

  • The drug name is uncommon and could be confused with a similar one
  • You want to verify that PharmGKB has the exact compound (not just a related congener)

Why this works — the mechanism:

Discrete node lookup surfaces "did-you-mean" errors that dense retrieval smooths over.

Text embeddings are optimised to bring semantically similar things together. That's the right behaviour when the retriever's job is to find relevant chunks — but it's the wrong behaviour when the LLM needs to know whether the user's exact entity name is correct.

  • A1's retriever maps "methazolamide" to embeddings that are cosine-close to "acetazolamide" — same drug class, same metabolic pathway. It returns acetazolamide chunks, and the LLM produces a fluent answer that treats them as if they were about methazolamide. The disambiguation error is silent.
  • A3's entity linker does exact + fuzzy string matching with a tight threshold (score ≤ 0.18). Near-misses fail to link. When methazolamide fails to match and acetazolamide is not in the question, the linker returns just HLA-C — the LLM sees a lopsided context and can flag: "the drug you named isn't in the graph."
  • A0 has no retrieval feedback at all and answers as if the user's spelling is authoritative.

The concrete win, from the eval: A3 explicitly noted "catches the critical entity mismatch: acetazolamide vs. methazolamide" — a signal only the discrete linker can produce.

Pattern 4 · "Patient carries <wild-type allele> — what to avoid?" — premise-questioning queries

4 of 5 substantive S3 (multi-hop) wins follow this pattern.

When a question implicitly assumes a variant carries clinical implications, but the named allele is actually wild-type (e.g., CYP2C19*1, CYP2D6*1, CYP2C9*1, SLCO1B1*1), GraphRAG's structured context with explicit evidence-level tags (L1A, L2A, CRITICAL) helps frame the response: "this is the reference allele — no avoidance — but if a variant were present, here's what the graph says." Other arms sometimes drift into giving avoidance advice for the wild-type.

Example prompt (real, from the eval — question S3-022):

"A patient is found to carry the CYP2D6*1 variant in CYP2D6.
Which class of medications may require dose adjustment, and why?"

Why A3 wins:

  • A3 sees the full graph context (CYP2D6 → opioids, tramadol, etc., with evidence levels).
  • The structured rendering helps the model produce a properly-hedged "wild-type → no adjustment, but here is the L1A/CRITICAL context if a variant were present" answer.
  • A0 sometimes gives confidently-wrong avoidance advice; A1's retrieved chunks lack the wild-type/variant disambiguation.

Why this works — the mechanism:

Structured evidence-level tags travel intact through the prompt; prose retrieval strips them.

Correctly answering "patient has CYP2D6*1, what to avoid?" requires the model to (a) recognise *1 is wild-type, (b) hedge properly — no specific avoidance is warranted — and (c) offer the L1A/CRITICAL context that would apply if a real variant were present. The third step needs evidence-level metadata, not prose.

  • A3's rendered subgraph puts the metadata inline, one per line: sevoflurane --is linked to risk of[L1A, CRITICAL]--> RYR1. Every edge is tagged. The LLM can copy the tags into its answer verbatim — "the L1A CRITICAL context around this gene is X, Y, Z" — without having to remember or reconstruct them.
  • A1's text chunks contain the same metadata but scattered across prose descriptions of clinical variants. The tokens 1A and CRITICAL aren't near their subject; the LLM has to reconstruct the binding relationally, and often drops or misattributes evidence levels in the summary.
  • A0 has no evidence levels at all — it either omits them (vague answer) or invents them (confidently wrong).

Judge reasons in the eval consistently praised A3's answers for "including exact evidence-level classifications (L1A CRITICAL, L2A) that align with actual CPIC/PharmGKB standards" — that fidelity is what the structured rendering buys.

Counter-pattern — where A3 LOSES on this stratum:

23 of 40 S3 questions went to A1 — most are real rs-ID variants (rs2108622, rs1801160, rs121918596, rs9923231, etc.) where PharmGKB rows pack drug + gene + variant + class into a single denormalised chunk. A1's hybrid retriever finds the chunk directly; A3's graph traversal adds no benefit. The pattern: denormalised single-row lookups are where plain-text RAG wins, not where graph traversal wins.

B.3 — When NOT to use GraphRAG (where A1 / A0 actually beat it)

Symmetry: from the same data, here's where GraphRAG should not be the system you reach for.

  • Easy / well-known pharmacogenomic facts (S1). A3 won only 35% of pairwise comparisons here vs A1. The graph context adds noise on questions any reasonable LLM answers from training (e.g., "which gene is most strongly associated with malignant hyperthermia?" → RYR1, no graph needed).
  • Specific evidence-level lookups (S2). A3 won 44% — basically a tie. PharmGKB rows already pack evidence levels into single text chunks, so text retrieval recovers them efficiently.
  • Real rs-ID variant → drug-class queries when the variant is a canonical PharmGKB row (S3 majority). A1 wins these because the variant-row is retrievable as a single text chunk.
  • Citation-only queries (S4). Confounded — A3 sometimes "wins" because the judge prefers its refusal over A1's correct citation. Use A1 (or hybrid) when you explicitly need PMIDs.

B.6 — A general framework: what kind of prompt should favour GraphRAG?

Looking across every winning candidate (the 4 double-winners plus the 6 single-arm winners), a mechanism-level pattern emerges. GraphRAG wins when the prompt requires an answer that depends on a small, specific subgraph the LLM cannot reproduce from memory — not when it requires generation from a large body of related text (which text retrieval does fine).

Concretely, GraphRAG's advantage is largest when all three of these are true:

  1. The named entities are in the graph but the edge between them is not. The value is negative information — "these two things exist as nodes, but no relationship connects them." Text retrieval cannot easily produce absence; it always returns something and the LLM interprets that as evidence. GraphRAG's entity-linker finds both nodes, its neighborhood expansion enumerates every actual edge, and the model can honestly report the missing one.
  2. The correct answer needs to distinguish similar-looking entities. Wild-type vs. variant alleles (CYP2C9*1 vs. CYP2C9*3), a misspelled drug name that resolves to a different entity, a chemical vs. its formulation. GraphRAG's exact-node lookup — "does the graph have this exact string?" — forces the LLM to face the disambiguation. Text similarity papers over near-misses.
  3. Structured metadata on the edges matters. Evidence levels (1A, 1B, L2A), CRITICAL flags, edge types (can_trigger, affects_response_to). GraphRAG's context surfaces these as inline tags on every edge, giving the LLM material to hedge, prioritise, or refuse with. Text retrieval loses them in prose flow.

If none of these are true — the question is about a well-known drug-gene pair, a single canonical row in a denormalised table, or a "list all X" that any text search can answer — plain-text RAG will typically match or beat GraphRAG.

A simple predictive checklist

Score a candidate prompt on these 4 questions before spending compute to evaluate it:

QuestionIf yes, favours GraphRAG because…
Does the prompt ask about the absence or presence of a specific relationship?Absence is what graph traversal proves cleanly.
