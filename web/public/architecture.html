Two parallel surfaces over the same PharmGKB knowledge graph:

(1) An interactive web app (Cytoscape graph canvas + Explain/Chat panels) that runs the subgraph-RAG retrieval in the browser and calls an LLM.

(2) A reproducible evaluation framework that tests whether the graph layer adds value over plain-text RAG and parametric-only baselines.

Looking for the step-by-step reproduction recipe with commands and per-metric explanations? That lives in Appendix A of the eval report — kept beside the results it produces.

1. The three pieces

PieceWhat it doesWhere in repo
Data pipeline Turns raw PharmGKB TSVs into the JSON knowledge graph used by both surfaces. preprocess/build_graph.py
Web app Next.js 14 + TypeScript + Cytoscape. Renders the graph, runs subgraph-RAG retrieval in the browser, calls an LLM. Two deploy targets (local + Firebase). web/
Eval framework Python pipeline that reproduces every metric in the eval report. Deterministic, resumable, all evidence committed. eval/

2. Data flow in plain English

Six raw PharmGKB TSVs (~160k rows total) live at the repo root. preprocess/build_graph.py parses them and writes three JSON files into data/:

  • data/graph.json — 3,213 nodes, 8,024 typed edges with evidence levels and PMIDs
  • data/seed_anesthesia.json — the 36-node demo subgraph (anesthesia / malignant hyperthermia)
  • data/search_index.json — flat entity index for autocomplete and entity-linking

Both consumers read these files:

  • The web app loads them at runtime (server-side via API routes locally, browser-side fetch in the static Firebase build) and uses them to render the canvas, autocomplete searches, and do subgraph-RAG retrieval at query time.
  • The eval framework uses a held-out variant (data/graph_heldout.json, produced by eval/rebuild_heldout.py) so neither the system under test nor any baseline can "look up" the test questions.

The key file in the web app is web/lib/graph/retrieve.ts — that's where the GraphRAG retrieval actually happens. It's faithfully ported to Python in eval/retrieve_py.py so the eval tests the real algorithm, not a re-imagined one.

6. Tech stack at a glance

  • Preprocessing: Python 3 stdlib only — no pip dependencies (intentionally)
  • Web app: Next.js 14 · TypeScript 5.5 · React 18 · Tailwind 3.4 · Cytoscape.js (fcose) · Zustand · Fuse.js · Radix UI · CVA · lucide-react
  • Backend (local): Next.js API routes spawning claude -p via Node child_process
  • Backend (deployed): Firebase Hosting + Cloud Functions v2 (Node 20) + Secret Manager for the LLM key
  • Eval pipeline: Python 3.12 · rank_bm25 · sentence-transformers (all-MiniLM-L6-v2) · rapidfuzz · Claude CLI for generation and judging
  • Eval models: Claude Sonnet 4 (generator) · Claude Haiku 4.5 (judge)
