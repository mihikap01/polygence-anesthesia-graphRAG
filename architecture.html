Polygence pharmacogenomic graph-RAG · code architecture

How the system is built

Author: Mihika Pall. A walkthrough of the codebase — what each module does, how the pieces connect, and how the live demo and evaluation framework relate.

Live demo → Eval report → GitHub →

The project ships two parallel surfaces over the same PharmGKB pharmacogenomic knowledge graph:

(1) An interactive web app — a Cytoscape-rendered graph with Explain (click a node/edge) and Chat (free-form question) panels. Both panels do GraphRAG retrieval and feed the result to an LLM (Claude CLI locally, Gemini via Firebase Cloud Function in production).

(2) A reproducible evaluation framework — 187 held-out questions × 3 retrieval conditions (no-context, plain-text RAG, subgraph RAG) × 4 metric families (rule-based, pairwise preference, rubric, hallucination via merged-claim segmentation). All scripts and raw evidence committed.

2. Data pipeline

One script (preprocess/build_graph.py, Python stdlib only) turns the six raw PharmGKB TSVs into three JSON artifacts under data/:

FileSizeWhat's in itConsumers
graph.json~2 MB3,213 nodes (drug / gene / variant_cluster / drug_class / phenotype) + 8,024 typed edges with evidence levels, PMIDs, and CRITICAL flagsWeb app graph canvas, Explain/Chat retrieval; eval A3 (subgraph RAG)
seed_anesthesia.json~28 KBThe 36-node anesthesia / MH demo subgraph used as the default viewWeb app initial load
search_index.json~302 KBFlat list of {id, label, type, alt} for entity-linking and autocompleteLeftSidebar search, eval A3 entity-linker

Held-out variant of the pipeline (for eval fairness)

The same build script honours two env vars to produce a reduced graph for the evaluation:

HELDOUT_VARIANTS=eval/heldout_variant_hashes.txt \
HELDOUT_OUTPUT=graph_heldout.json \
python3 preprocess/build_graph.py
# → data/graph_heldout.json (3,203 nodes, 7,972 edges)
# → data/search_index_heldout.json (same shape, reduced)
# → data/seed_anesthesia_heldout.json

3. Web app architecture

Next.js 14 App Router. TypeScript throughout. Cytoscape for the graph canvas, Tailwind + small custom CSS for the rest. State held in a Zustand store. Two build targets: server (API routes active, Claude CLI) and static export (BYOK to the user's LLM key).

Frontend modules

app/page.tsx — three-pane layout, loads seed graph on mount.

app/about/page.tsx — about + author + links.

components/GraphCanvas.tsx — Cytoscape (fcose layout), click handlers, filter classes.

components/LeftSidebar.tsx — entity search + filter toggles + dataset loaders.

components/RightSidebar.tsx — Explain panel (click-driven) and Chat panel (question-driven). Includes the "Context sent to model" viewer.

components/ApiKeyModal.tsx — BYOK modal for static deploys.

components/ui/{Button,Input,Dialog}.tsx — Radix UI + CVA primitives.

Graph / LLM lib

lib/graph/types.ts — Graph, GraphNode, GraphEdge, SearchHit.

lib/graph/ops.ts — pure ops (neighbourhood, applyFilters), browser-safe.

lib/graph/loader.ts — server-side fs reads of data/*.json.

lib/graph/runtime.ts — process-wide cache for the search index.

lib/graph/client-loader.ts — browser fetch of static JSONs (BYOK mode).

lib/graph/data-api.ts — facade: API route vs. in-browser ops by env.

lib/graph/retrieve.ts — GraphRAG core: entity link → neighbourhoods → BFS shortest paths → structured packet.

lib/llm/{index,openai,claude-cli,prompts}.ts — provider abstraction.

lib/llm/browser.ts + browser-pipeline.ts — BYOK browser-side LLM calls.

API routes (active only in server build)

RouteWhat it does
/api/graphReturns seed view or N-hop neighbourhood around a seed node.
/api/searchReturns the search index for autocomplete.
/api/explainGiven (kind, id), runs nodeContext/edgeContext retrieval → LLM → returns answer + retrieved subgraph.
/api/chatGiven a question, runs retrieveForQuestion → LLM → returns answer + retrieval (entities, paths, subgraph size).

4. Two deploy targets

Local dev

npm run dev → http://localhost:3000

Server build with API routes active. LLM_PROVIDER=claude-cli in .env.local — every Explain/Chat call spawns claude -p headlessly, reusing your Claude Code auth. No API keys needed.

Firebase Hosting

npm run deploy:firebase

Static export (output: "export") shipped to polygence-pubmed-graphrag.web.app. The retrieval pipeline runs in the browser (graph.json fetched once + cached). LLM calls go to /api/llm which is rewritten by Hosting to a Firebase Cloud Function (functions/index.js) that calls Gemini with GEMINI_KEY stored as a Firebase secret. The key never enters the JS bundle.

Alternatively the user can paste their own OpenAI/Anthropic/Gemini/DeepSeek key in the in-app modal → browser calls the provider directly.

6. End-to-end flow for one question

To make the abstraction concrete, here's what happens when a user asks "Why is sevoflurane risky for malignant hyperthermia?" on the live web app:

1. Browser (RightSidebar Chat panel)
   user types question → fetch POST /api/llm   (BYOK build via Firebase rewrite)

2. Firebase Hosting (firebase.json rewrite)
   /api/llm → Cloud Function `ask` (us-central1)

3. Browser-side retrieval — BEFORE the POST, runs lib/graph/retrieve.ts:
   ┌──────────────────────────────────────────────────────────┐
   │ a) link_entities(question, graph)                         │
   │    → fuzzy match against 3,213 nodes via Fuse.js          │
   │    → finds: sevoflurane (drug), Malignant Hyperthermia    │
   │      (phenotype), isoflurane (drug, fuzzy-match noise)    │
   │                                                            │
   │ b) For each linked entity: neighborhood(graph, [id], 1)    │
   │    → BFS over adjacency list, 1 hop                        │
   │    → ~22 edges connecting them to RYR1, succinylcholine,  │
   │      Volatile Anesthetics class, etc.                      │
   │                                                            │
   │ c) shortest_path between every pair of linked entities     │
   │    → BFS, max 4 hops, preferring CRITICAL / L1A edges      │
   │    → 3 paths surfaced                                      │
   │                                                            │
   │ d) Render as structured text:                              │
   │    ENTITIES IDENTIFIED:                                    │
   │      • sevoflurane (drug) — matched "sevoflurane"          │
   │      • Malignant Hyperthermia (phenotype) — ...            │
   │    DIRECT NEIGHBOURHOOD OF sevoflurane:                    │
   │      - sevoflurane --is linked to risk of[L1A, CRITICAL]   │
   │        --> RYR1                                           │
   │      - sevoflurane --can trigger[L1A]--> MH               │
   │      - sevoflurane --belongs to drug class--> Volatile... │
   │    SHORTEST REASONING PATHS:                               │
   │      sevoflurane → RYR1 → MH (2 hops, CRITICAL)            │
   └──────────────────────────────────────────────────────────┘

4. POST /api/llm with {systemPrompt, userPrompt} where userPrompt =
   structured context block + the original question.

5. Cloud Function (functions/index.js)
   • Origin check (only *.web.app + localhost allowed)
   • Per-IP rate limit (in-memory, 20/min/instance)
   • Forwards to api.deepseek.com or generativelanguage.googleapis.com
     with the secret key

6. Response flows back through the Cloud Function → browser
   • RightSidebar renders the answer with PMIDs as link chips
   • "Context sent to model" panel shows the exact prompt for inspection
